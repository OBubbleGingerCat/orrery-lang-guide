# 把模型写好

用法指南讲 Orrery 的每样东西做什么。这份教程讲怎么把它们搭在一起，让模型：

- **跑得快**：单线程、多线程都花时间少；
- **好读**：一个单元的行为在一处看得全，读的人要同时记住的东西少；
- **多开线程更快**：8 线程的时间比 1 线程少得多。

每一章讲一种写法：什么情况下用、怎么写、怎么确认写对了。每章还说这种写法对上面三条各有什么影响，数取自一个能编译、能运行的例子。第 1 章教怎么在自己的模型上量这三条，后面每一章都照这个办法量。

## 三条怎么量 {#the-three-measures}

| 指标 | 量什么 | 怎么量 |
|---|---|---|
| 快 | 1、2、4、8 线程各自跑的时间，建仿真另计 | 自己写驱动程序，每个线程数跑三次取中位数（[第 1 章](./measure)） |
| 加速比 | 1 线程时间 ÷ *N* 线程时间，和时间本身一起报 | 同上；再记下装载报告给的、每个线程数的执行单元数 |
| 好读 | (a) 行数；(b) 读懂一个单元要同时记住几样东西：它的 task、它的门、谁叫醒它、它的 task 和别的 task 在一拍里靠什么排先后；(c) 一个硬件单元的行为是不是在一处看得全 | 改前、改后各数一遍 |

## 三条打架时怎么取舍 {#when-the-three-disagree}

拿改动和改之前的模型，一个线程数一个线程数地比。相差 10% 以内算抖动。

- **更好**：没有哪个线程数变慢，至少一个线程数快出抖动。那就改，并用一句话说它在 8 线程上是快、一样还是慢。
  - 加速比照报，但不要因为加速比降了，就否掉一个处处更快的改动。一个让 1 线程快很多的改动，可能让剩下可分的活变少。[第 8 章](./arbitration)有这样的例子。
- **有快有慢**：有的线程数快、有的慢。没有通用的答案，按自己要跑的线程数选：
  - 主要跑 8 线程，就取 8 线程快的；
  - 两样都跑，把两头的时间和改动对可读性的影响写进一张表，自己定。
- **更好读、速度一样**：取好读的。
- **更好读、但慢出抖动**：写明慢多少，自己定。

## 每章怎么写 {#how-the-chapters-are-written}

每章都有这几部分：

- 规则：什么情况下用，怎么写，怎么核对；
- 一个能整个读完、能编译运行的例子；
- 这条规则在例子上对三条指标的影响；随 Orrery 附带的 GPU 模型上有量过的情形时，也给出来；
- 什么时候不该这样写；
- 一张核对单。

**例子**是一个 Cargo 包。它的库就是第 1 章的计时帮手，每章一个可执行程序。运行一个：

```sh
cargo run --release --bin ch1_measure
```

每个例子对每个线程数打一行：运行时间、加速比、建仿真时间、执行单元数、一个校验和。校验和不能随线程数变，同一件事的两种写法之间也不能变。

**数**：除非某章另外说明，本教程里的数都是粗量。每个数是三次运行的中位数，在 8 个没有别的活的核上跑。你的机器会给出不同的时间，比的是比值。
